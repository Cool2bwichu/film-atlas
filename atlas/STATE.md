## Build

```bash
node app/build.js                                  # -> atlas.html, whole corpus
node app/build.js --films 220 --degree 10 --out atlas-artifact.html
```

Corpus rebuild, in order. Every networked stage caches and is resumable:

```bash
node pipeline/harvest-sparql.js pipeline/seeds.txt   # ~40 SPARQL queries
node pipeline/enrich.js                              # posters, descriptions, TMDB keywords
python3 pipeline/palette.py                          # colour measured from each poster
node pipeline/associate.js && node pipeline/merge-corpus.js
node pipeline/validate-corpus.js && node pipeline/measure-maps.js
node pipeline/measure-claims.js                      # trivia share — the quality number
```

`TMDB_KEY` adds keywords. Posters move only under `TMDB_POSTERS=1`, which also
requires re-running `palette.py` since the palettes are measured from them.

## Known open problems, in priority order

1. **Scaling to thousands of films will break the calibrated thresholds, and
   quietly.** The corpus is now 2,204 and the target is larger still. Two known
   hazards, both measured:

   - `idf(n,N) = log(N/n)/log(N)` is N-dependent, and it does not drift in one
     direction. An attribute whose absolute count stays fixed as the corpus
     grows scores *higher*; one that grows with the corpus scores *lower*. A
     keyword in 30 films scores 0.491 at N=803 and 0.631 at N=10,000; one that
     scales to 375 films scores 0.356. So growth **reshuffles the ranking
     between attribute types** rather than loosening it uniformly. Every
     `floorIdf` in `SIGNALS` was hand-calibrated at N=803 and none of them will
     mean the same thing at N=5,000.
   - The pair space grows as N². The chance two unrelated films share three
     keywords by accident rises with every film added, so any rule phrased as
     an absolute count gets weaker as it scales, silently.

   The keyword signal is already converted: its strength comes from
   `surprise()`, a Poisson tail against the overlap expected from the corpus's
   own frequencies. **The other signals have not been converted** — subject,
   setting, cast, movement and studio all still gate on raw `floorIdf`.

   **Measured, 2026-08-07 — the drift is real but much smaller than this entry
   assumed.** `pipeline/measure-scale.js` now reports it instead of arguing it.
   Produced by exactly this invocation — quote the flags with the table, the
   numbers differ without them:

   ```bash
   node pipeline/measure-scale.js --cohort pipeline/cohort-pre-growth.txt --pairs 400000
   ```

   ```
   countryEra 1.01x   setting 1.04x   cast 1.05x   genre 1.06x
   movement   1.09x   genreEra 1.12x  studio 1.13x  subject 1.17x
   keyword (surprise, the scale-free control)      1.12x
   ```

   Every `floorIdf` signal drifts within the control's own margin. The worst,
   `subject` at 1.17x, is 1.0x the control. So over the measurable range the
   conversion is **not** urgent, and the earlier "~2.0x vs ~3.9x" figures did
   not survive being measured with a noise guard.

   Three caveats, all load-bearing:

   - This measures 550→803, a 1.46x growth. Going to 2,000 is 2.5x again, and
     the analytic argument above is still mathematically true — `idf` is
     N-dependent whatever the current sample says. Small drift over the range
     we can see is **not** proof of small drift beyond it.
   - `sameAuthor` is not measurable at any N this corpus reaches: it fires on
     ~0.01% of pairs, so even 400k sampled pairs yield 18 events. The tool now
     prints `noisy` with the event count rather than a ratio. Its first run
     reported a confident **6.35x** for `sameAuthor` built on about twelve
     events, and a 2.68x "control" built on eleven — both pure noise. Any drift
     figure quoted without its event count should be distrusted.
   - `usable()` is not modelled, so absolute percentages read high by a constant
     factor. That factor cancels out of the ratio, which is why the ratio is the
     column to read.

   **The tool is structurally blind to the thing most likely to go wrong.**
   `GATED` covers only floorIdf signals, so `crew` — which gates on identity,
   not rarity, and is the signal that swamps the edge budget as the corpus
   grows — is not in the table at all, nor are `MAX_EDGES_PER_VALUE` or the
   one-edge-per-pair contest. A clean drift table is **not** a clean bill of
   health: it can read all-green while half the graph turns into filmography
   browsing. Read `measure-claims.js` at its `crew %` and `REPEATED` lines for
   that failure, not `TRIVIA SHARE`.

   **Re-run after a harvest with `--cohort pipeline/cohort-pre-growth.txt`.**
   An earlier version of this entry said to re-run the bare command and read the
   extended ladder as the answer. That was wrong, and wrong in the way that
   reads as a regression: `subsample()` takes the n lowest key hashes, so the
   "N=803" rung of a 2,000-film corpus is a hash-selected 803 films, not the 803
   in the corpus today — `subject` reads 0.55% here and 0.30% there, same tool,
   same flags, different films. `pipeline/cohort-pre-growth.txt` freezes today's
   803 so both sides of the harvest name the same films. Without it, compare
   drift ratios only, never absolute rates.

2. **Claim quality: 23.0% trivia — and the number went UP, because the corpus
   grew.** Seven reading passes took it 36.1 → 30.4 → 29.7 → 27.7 → 25.7 →
   23.8 → 20.9 at N=803; the harvest to 2,204 then dragged it back to 23.0%,
   because 1,401 new films arrived carrying record coincidence and no reading.
   **Ranking is not the lever; attributes and readings are.** The "films with no
   reading" lever, which this entry once recorded as spent, is wide open again:
   **1,324 of 2,204 films carry no reading at all.** That is where the trivia
   share is hiding. Read the keyword block in `associate.js` before touching
   keyword scoring — rarity is the WRONG test for a keyword and the comment
   explains why at length.

   `crew` is the number to watch beside it: **40.3% of every line a reader
   sees**, and it is the failure mode a clean trivia figure cannot show you,
   because "shares a cinematographer" is checkable, unfalsifiable and teaches
   nothing. See `pipeline/signature-schema.md` for the intended answer.

   Note the shape of the seventh pass: `record` edges FELL by 89 while readings
   rose 199. Authored claims displace record coincidence on pairs that now
   carry a reading, so the totals do not simply add.

3. **Edge labels can still overlap posters at desktop.** Improved but not
   solved; the collision test now measures real label boxes.

4. **Untested:** touch on a real phone; behaviour under an artifact CSP.
5. Corpus payload is 13.4 MB, and the built artifact 8.8 MB — fine on a
   desktop connection, genuinely heavy on mobile. It was 3.6 MB at N=803.

## Traps that have already cost time

- **jsdom cannot tell you a page is visible.** It mounts and evaluates; it does
  no layout and no paint. Two handoffs passed it while rendering a black
  screen. Open it in a browser and look.
- **A rule that reads as "variety" can be a trivia quota.** Guaranteeing one
  edge of each type reserved a seat for `convergence`, which is 100%
  genre-and-era coincidence.
- **Weak ties are load-bearing.** Deleting them makes 42% of films dead ends.
  They exist to keep the graph traversable, not to be read — rank them last,
  never remove them.
- **A single enormous line breaks renderers.** Keep embedded data chunked.
- In this sandbox, a bash call that times out kills detached background jobs.
- **Behind an egress proxy, SPARQL over GET fails where POST succeeds.** From
  the Claude-on-the-web container, `GET query.wikidata.org/sparql?query=…`
  returns a bare nginx `502` for any real query while the same query over POST
  returns 200, and `GET /sparql` with no query returns 200 — so a naive reach
  test says the endpoint is fine and every actual query fails. `harvest-sparql.js`
  already POSTs and is unaffected; do not "simplify" it to GET.
- **`enrich.js` will silently destroy every measured palette.** `palette.py`
  writes its results back into `enrich.json`, which `enrich.js` rewrites from
  scratch. The loss is invisible — the corpus still builds and every film still
  has a colour, just an era default instead of a measured one. `enrich.js` now
  carries palettes forward when the poster URL is unchanged and prints the
  count. Check that line after any enrichment run.
- **A metric can improve while the thing it measures gets worse.** The first
  keyword build cut trivia 36% → 9% and made the maps worse: the trivia had
  moved inside the keyword signal, which `measure-claims.js` was not counting.
  Read the sampled maps, not just the number.
- **The browser will serve you a stale `atlas.html`.** It is 2 MB and caches
  hard; a reload after a rebuild can show the previous build. Append `?v=N`.
  A black screen that "came back" after a fix is usually this.
- **`artifact/`, `local/` and `scripts/` are dead code**, not alternate paths.
  `scripts/build-single.js` still regenerates the React build that rendered
  black. The only build command is `node app/build.js`.
